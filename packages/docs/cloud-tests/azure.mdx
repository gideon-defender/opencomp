## About the Azure integration

OpenComp connects to Microsoft Azure to pull security posture, identity, network, and compliance data from **Microsoft Defender for Cloud** and related services. All access is scoped to read-only unless you opt in to auto-remediation with separate per-class service principals.

The recommended connection method is **Microsoft OAuth** — you sign in with an Azure AD account that has the required roles, and OpenComp auto-detects your subscription. A **service principal** flow is also supported for customers who prefer to provision a dedicated identity.

<Note>
  Scans are read-only: OpenComp only issues `GET`/`list` API calls with the auditor identity. It
  creates, modifies, or deletes resources only through a bound remediator service principal, and
  only when you explicitly trigger a fix.
</Note>

## How access works

- **Primary flow**: OAuth 2.0 against `login.microsoftonline.com` using the `user_impersonation` scope on Azure Management API. OpenComp acts on behalf of the signed-in user, constrained by their Azure RBAC assignments.
- **Alternative flow**: An Azure AD App Registration (service principal) with a client secret, assigned the required roles on a subscription.
- **Scope**: A single Azure subscription per connection. Connect additional subscriptions by adding more connections.
- **Optional auto-remediation**: Separate per class x subscription service principals (`opencomp-remediator-<class>`, e.g. `opencomp-remediator-storage`) can be bound to enable auto-fix actions — each SP is **only used when you explicitly trigger a fix** for a matching finding. The auditor identity stays read-only.

## Prerequisites

Before connecting Azure, make sure you have:

1. An **Azure subscription** you want to monitor
2. A user (or service principal) with the following roles on that subscription:
   - **Reader** — read resource metadata
   - **Security Reader** — read Microsoft Defender for Cloud findings
   - **Monitoring Reader** — read activity logs, alerts, and metrics
3. **Microsoft Defender for Cloud** enabled on the subscription (the free tier is sufficient for most checks)
4. Admin access to your OpenComp workspace

## Connect with OAuth (recommended)

<Steps>
  <Step title="Start the connection">
    In OpenComp, go to **Cloud Tests → Azure → Connect**. Click **Sign in with Microsoft**.
  </Step>
  <Step title="Consent to the requested scopes">
    Sign in with an Azure AD account that has the roles listed above on the target subscription. Approve the consent screen.
  </Step>
  <Step title="Verify detected subscription">
    OpenComp automatically detects the subscriptions your account can access. The setup guide then runs checks for:

    - **Subscription detected**
    - **Required role assignments**
    - **Defender for Cloud enabled**

    Any blocking issue is shown with a link to the exact Azure portal blade to fix it.

  </Step>
  <Step title="Run your first scan">
    When all required steps pass, the first scan starts automatically. You can re-run it any time from the connection's page.
  </Step>
</Steps>

<Note>
  Microsoft OAuth uses the RBAC roles on your account. Granting **Reader + Security Reader +
  Monitoring Reader** is enough — you do **not** need Contributor or Owner.
</Note>

## Connect with a service principal (alternative)

Use this flow if you want a dedicated non-human identity or your tenant restricts user OAuth consent.

<Steps>
  <Step title="Register an app in Microsoft Entra ID">
    In the Azure portal, go to **Microsoft Entra ID → App registrations → New registration**. Name it something like `comp-security-audit` and register.
  </Step>
  <Step title="Create a client secret">
    In the app, open **Certificates & secrets → New client secret**. Copy the secret **value** immediately — it is only shown once.
  </Step>
  <Step title="Assign the three required roles">
    Open your target subscription, go to **Access control (IAM) → Add role assignment**, and assign each of these roles to the app registration:

    - **Reader**
    - **Security Reader**
    - **Monitoring Reader**

  </Step>
  <Step title="Collect the four IDs">
    From the Azure portal, copy:

    - **Tenant ID** — Microsoft Entra ID → Overview
    - **Client ID** — App registration → Overview (Application ID)
    - **Client Secret** — the value from the previous step
    - **Subscription ID** — Subscriptions → your subscription

  </Step>
  <Step title="Paste into OpenComp">
    In the Azure connection form, switch to the service principal option and paste the four values. Click **Save and Connect**.
  </Step>
</Steps>

## What gets scanned

The Azure integration evaluates findings across services including:

| Area          | Services                                               |
| ------------- | ------------------------------------------------------ |
| Posture       | Microsoft Defender for Cloud (assessments + alerts)    |
| Identity      | Microsoft Entra ID                                     |
| Governance    | Azure Policy                                           |
| Data security | Key Vault, Storage Accounts, SQL Database, Cosmos DB   |
| Compute       | Virtual Machines, App Service, AKS, Container Registry |
| Network       | Network Watcher (NSGs, flow logs)                      |
| Observability | Azure Monitor (activity logs, diagnostic settings)     |

The **Services** tab inside the connection lets you enable or disable specific checks.

## Compliance frameworks

Findings are mapped to the controls used by:

- Microsoft Cloud Security Benchmark
- SOC 2
- ISO 27001
- PCI DSS
- HIPAA (where applicable)

## Set up auto-remediation (optional)

If you want OpenComp to apply fixes, bind one remediator service principal per asset class x subscription pair. Start with the classes you want auto-fix in (`Storage`, `Compute`, `Data`).

<Steps>
  <Step title="Run the setup script per pair">
    In the connection settings, open the remediation binding for the class x subscription pair and run the generated script in Cloud Shell with subscription Owner on that subscription. Each script creates a dedicated `opencomp-remediator-<class>` service principal, carves a narrow fix-forward custom role for that class, and assigns it at subscription scope. Safe to re-run: existing principals and role definitions are reused and updated in place.
  </Step>
  <Step title="Paste back the binding">
    The script prints a `Class:subscription` entry holding the SP application (client) ID. Paste it into the matching row of the remediation table and store the shown-once client secret in the connection vault — secrets live vault-only and are never returned to the UI.
  </Step>
  <Step title="Leave gated classes human-approved">
    `Network` and `Security-Global` findings never auto-execute, even with a principal bound. Fixes for those classes stay guided-only until a human approves them.
  </Step>
</Steps>

## Security model

- **Read-only by default** — scans use the auditor identity and issue no write calls; fixes authenticate as the bound class service principal only when you trigger them
- **Scoped to one subscription per connection** — a connection cannot read data outside the subscription it was created for
- **Secrets stay encrypted** — client secrets and refresh tokens are stored in an encrypted vault and never returned to the UI
- **Revocable at any time** — remove the role assignments in the Azure portal, or delete the connection in OpenComp
- **Fix-forward allowlist** — when auto-remediation is enabled, fix plans execute only through a per-class ARM method+prefix allowlist, and plans touching never-allow actions (role-assignment/definition writes, vault deletes, wildcard grants) or privileged roles (`Owner`, `Contributor`, `User Access Administrator`) are refused before execution

## Monitoring auto-remediation

If you bound any `opencomp-remediator-*` service principals, watch them. OpenComp only authenticates as a remediator SP when you explicitly trigger a fix, so every write outside a fix you triggered is worth a look. Three signals matter:

| Signal                                                        | What it means                                                                                                             | Severity                                  |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| Succeeded control-plane write by a remediator SP              | A fix ran (one alert per class, e.g. `OpenComp-RemediatorWrite-Storage`)                                                    | Info — reconcile with fixes you triggered |
| Failed call from a remediator SP session                      | A fix hit a failure — usually an allowlist/guardrail-blocked write that reached the API anyway                              | Low — investigate if repeated             |
| Remediator write to an approval-gated surface                 | Role-assignment, role-definition, or vault writes from a remediator SP (never auto-executed)                                | High — every use needs a human review note |

Subscribe the security on-call email — not an individual inbox. Confirm the action-group verification email before expecting alerts. Key Vault data-plane activity is blind to Activity Log (it needs diagnostic settings, not Activity Log) — the vault signal above covers control-plane writes only.

<Steps>
  <Step title="Create the action group and alert rules">
    Run in Cloud Shell with subscription Owner on the subscription holding the remediator SPs (or ask support for the generated script):

    ```bash
    SUBSCRIPTION="12345678-1234-1234-1234-1234567890ab"
    RESOURCE_GROUP="rg-opencomp"
    az monitor action-group create --name "OpenComp-Remediator-Alerts" --resource-group "$RESOURCE_GROUP" --short-name "OpenComp" --email-receiver name=NotifySecurity email_address="security@example.com" --query id --output tsv
    az monitor activity-log alert create --name "OpenComp-RemediatorWrite-Storage" --resource-group "$RESOURCE_GROUP" --scopes "/subscriptions/$SUBSCRIPTION" --condition 'caller="<sp-app-id>" and category="Administrative" and status="Succeeded"' --action-group "<action-group-id>" --description "OpenComp: remediator service principal wrote"
    ```

    Repeat `activity-log alert create` per bound class (write + failed + one rule per approval-gated surface: role assignments, role definitions, vaults — see the detector source so alerts and queries cannot drift apart). The generated script deletes each rule before creating it, so reruns converge instead of failing.

  </Step>
  <Step title="Triage incoming alerts">
    - **Write alert**: match it to a fix you triggered in OpenComp. No match → check the caller app ID against your binding map and rotate that SP's secret.
    - **Failed alert**: read the operation name in the record. A 403 on a routine fix usually means the binding's custom role is missing a fix-forward permission — confirm the action was fix-forward before widening anything.
    - **Approval-gated alert**: confirm a human approved the action, then write the review note. If nobody did, treat it as an incident: these surfaces are human-gated by policy.
  </Step>
</Steps>

<Note>
  For forensics, the same three signals exist as KQL queries against the `AzureActivity` table
  (`azure-remediator-writes-7d`, `azure-remediator-denied-7d`,
  `azure-remediator-approval-gated-30d`) — route Activity Log to a Log Analytics workspace first,
  then paste the query. The exact queries live with the detector source.
</Note>

## Troubleshooting

<Accordion title="Defender for Cloud shows no assessments" icon="shield">
  Defender for Cloud must be enabled on the subscription. Open the **Microsoft Defender for Cloud**
  blade, select the subscription, and confirm at least the free tier is turned on. Initial data can
  take up to 24 hours to appear.
</Accordion>

<Accordion title="Authentication failed" icon="lock">
  For OAuth: make sure your account still has the three required roles on the subscription — `User_impersonation` scope alone is not enough.

For service principal: confirm the client secret has not expired and the app registration has not been disabled.

</Accordion>

<Accordion title="Subscription not detected after sign-in" icon="magnifying-glass">
  OpenComp only sees subscriptions your signed-in account has access to. If you manage multiple
  subscriptions, sign in with an account that has **Reader** on the one you want to monitor, or use
  the service principal flow to target it explicitly.
</Accordion>

<Accordion title="Missing findings for a specific service" icon="circle-exclamation">
  Check that the service is enabled under the **Services** tab for this connection. Some services
  also require Defender plans beyond the free tier — for example, Defender for Servers, SQL, or
  Containers.
</Accordion>

<Accordion title="Auto-remediation isn't available" icon="wrench">
  Auto-remediation requires a bound `opencomp-remediator-<class>` service principal for the finding's asset
  class and subscription. Run the setup script for that pair, then paste its `Class:subscription`
  entry into the remediation table in the connection settings. `Network` and `Security-Global`
  findings stay guided-only by policy, even with a principal bound.
</Accordion>
