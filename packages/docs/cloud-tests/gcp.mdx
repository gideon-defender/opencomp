## About the GCP integration

OpenComp connects to Google Cloud Platform over **OAuth 2.0** and reads findings from **Security Command Center (SCC)**. No service account JSON key is uploaded — you sign in with a Google account that has access to the organization and projects you want to monitor.

After you connect, OpenComp auto-detects your organization, lets you pick projects, then runs a setup step that enables the required APIs and verifies IAM access. Findings are mapped to common frameworks (SOC 2, ISO 27001, CIS GCP Foundations, PCI DSS, HIPAA).

<Note>
  Security Command Center is where all GCP findings originate. If SCC is not enabled at the
  organization, OpenComp cannot read findings regardless of connection method.
</Note>

## How access works

- **Auth model**: OAuth 2.0 with Google, using the `cloud-platform` scope plus `openid`, `email`, `profile` for account identification. Refresh tokens are stored so scans can run without re-prompting.
- **Real permissions**: The OAuth scope only enables API calls — actual access is gated by the **IAM roles** assigned to the signed-in account. OpenComp only makes read calls.
- **Required role**: `roles/securitycenter.findingsViewer` on the **organization** (needed to read SCC findings). Project-level `roles/viewer` is also recommended.
- **Scope**: OpenComp scans the projects you select inside the organization the signed-in account belongs to.

## Prerequisites

Before connecting GCP, make sure you have:

1. A **GCP organization** with **Security Command Center** enabled — confirm at **GCP Console → Security → Risk Overview**
2. A Google account with:
   - `roles/securitycenter.findingsViewer` on the organization
   - `roles/viewer` (or equivalent) on the projects you want to scan
3. Permission to enable APIs on at least one project in the organization (so OpenComp's setup step can enable SCC, Cloud Resource Manager, and Service Usage APIs if they are not already on)
4. Admin access to your OpenComp workspace

<Note>
  If Security Command Center is not yet enabled, enable it first at
  [console.cloud.google.com/security/command-center](https://console.cloud.google.com/security/command-center).
</Note>

## Connect GCP

<Steps>
  <Step title="Start the connection">
    In OpenComp, go to **Cloud Tests → GCP → Connect**. Click **Sign in with Google**.
  </Step>
  <Step title="Authorize with Google">
    Sign in with a Google account that meets the prerequisites above and approve the consent screen. OpenComp stores the resulting refresh token (never the password) so it can run scheduled scans.
  </Step>
  <Step title="Select projects">
    OpenComp auto-detects your organization and lists the projects that account can access. Pick the ones you want scanned — findings are scoped to those projects.
  </Step>
  <Step title="Let auto-setup run">
    OpenComp's setup guide runs automatically and shows a checklist:

    - Connected via OAuth
    - Organization detected
    - Required APIs enabled (Security Command Center, Cloud Resource Manager, Service Usage)
    - `roles/securitycenter.findingsViewer` granted at the organization level

    Any step that fails is shown with a one-click **Resolve** button or a link to the exact GCP console page plus the `gcloud` command you can run to fix it manually.

  </Step>
  <Step title="Run your first scan">
    When all required steps pass, the first scan starts automatically. You can re-run it any time from the connection's page.
  </Step>
</Steps>

## What gets scanned

OpenComp consumes findings from Security Command Center across services including:

| Area          | Services                                             |
| ------------- | ---------------------------------------------------- |
| Identity      | IAM (over-privileged accounts, service account keys) |
| Storage       | Cloud Storage (ACLs, public access, encryption)      |
| Compute       | Compute Engine, GKE                                  |
| Network       | VPC Network (firewall rules, flow logs), Cloud Armor |
| Data          | Cloud SQL, BigQuery, Pub/Sub                         |
| Cryptography  | Cloud KMS                                            |
| Observability | Cloud Logging, Cloud Monitoring                      |
| DNS           | Cloud DNS (DNSSEC)                                   |

The **Services** tab inside the connection lets you enable or disable specific check categories.

## Security model

- **Read-only in practice** — OpenComp only issues read API calls against SCC and resource manager
- **IAM-bounded** — access is limited to what the signed-in account's IAM roles permit
- **Token storage** — refresh tokens are stored in an encrypted vault; they are never returned to the UI
- **Revocable at any time** — remove the IAM role, revoke the token at [myaccount.google.com/permissions](https://myaccount.google.com/permissions), or delete the connection in OpenComp
- **Fix-forward allowlist** — when auto-remediation is enabled, fix plans execute only through a per-asset-class URL allowlist, and plans touching never-allow permissions (IAM writes, org-policy mutation, deletions) or privileged roles (`roles/owner`, `roles/editor`, service-admin roles) are refused before execution

## Monitoring auto-remediation

If you bound any `opencomp-remediator@<project>.iam.gserviceaccount.com` service accounts, watch them. OpenComp only mints a remediator token when you explicitly trigger a fix, so every impersonation outside a fix you triggered is worth a look. Three signals matter:

| Signal                                                  | What it means                                                                                              | Severity                                   |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| `GenerateAccessToken` on any `opencomp-remediator@*` SA | A fix ran (or someone probed impersonation — failed mints fire too)                                        | Info — reconcile with fixes you triggered  |
| `PERMISSION_DENIED` from a remediator SA session        | A fix hit a deny — usually an IAM-denied write the allowlist/guardrails would also have refused            | Low — investigate if repeated              |
| Remediator write to an approval-gated surface           | IAM, KMS, org policy, DNS, firewall/route, or IAM-policy writes from a remediator SA (never auto-executed) | High — every use needs a human review note |

Subscribe the security on-call email — not an individual inbox. Confirm the notification-channel verification email before expecting alerts. Denied _reads_ only appear when Data Access `DATA_READ` audit logs are enabled; denied writes are always logged. The impersonation signal needs Data Access `ADMIN_READ` logs for the IAM API (`GenerateAccessToken` emits a Data Access log, off by default) — the generated script turns that on; if you wire alerts by hand, enable it first.

<Steps>
  <Step title="Create the channel, metrics, and alerting policies">
    Run in Cloud Shell with an owner on the project holding the remediator SAs (or ask support for the generated script):

    ```bash
    PROJECT="my-proj-123"
    CHANNEL_ID=$(gcloud beta monitoring channels create --display-name="OpenComp Remediator Alerts" --type=email --channel-labels=email_address="security@example.com" --project="$PROJECT" --format="value(name)")
    gcloud logging metrics update opencomp-remediator-impersonate --description="OpenComp: remediator service account impersonated" --log-filter='protoPayload.serviceName="iamcredentials.googleapis.com"
    protoPayload.methodName="GenerateAccessToken"
    protoPayload.resourceName:"opencomp-remediator@"' --project="$PROJECT"
    ```

    Repeat `logging metrics update` (update, not create, so reruns converge) for `opencomp-remediator-denied` and `opencomp-remediator-approval-gated` with their filters (see the detector source so alerts and queries cannot drift apart), then create one alerting policy per metric firing on any match and targeting `$CHANNEL_ID`. Enable Data Access `ADMIN_READ` audit logs for the IAM API first — without them the impersonation metric stays empty.

  </Step>
  <Step title="Triage incoming alerts">
    - **Impersonation alert**: match it to a fix you triggered in OpenComp. No match → check for failed `GenerateAccessToken` calls (wrong-caller probes) in Logs Explorer and confirm the impersonator allowlist on the SA still names only the backend identity.
    - **Denied alert**: read `methodName` + `status` in the notification. An IAM `PERMISSION_DENIED` on a routine fix usually means the binding's custom role is missing a fix-forward permission — confirm the action was fix-forward before widening anything.
    - **Approval-gated alert**: confirm a human approved the action, then write the review note. If nobody did, treat it as an incident: these classes are human-gated by policy.
  </Step>
</Steps>

<Note>
  For forensics, the same three signals exist as saved Logs Explorer queries
  (`gcp-remediator-impersonations`, `gcp-remediator-denied`, `gcp-remediator-approval-gated`) — set
  the time range in the picker, since Logging filters take no relative window. The exact filters
  live with the detector source.
</Note>

## Troubleshooting

<Accordion title="Security Command Center findings not appearing" icon="shield">
  Confirm SCC is enabled at the organization level (not just one project). Open **GCP Console →
  Security → Risk Overview** and check that the organization shows findings.
</Accordion>

<Accordion title="Setup step: 'roles/securitycenter.findingsViewer' cannot be granted" icon="lock">
  The signed-in account does not have permission to manage IAM at the organization level. Ask a GCP
  organization admin to grant `roles/securitycenter.findingsViewer` to the account (or service
  account) you connected with. Copy the email shown in the setup guide — that is exactly who needs
  the role.
</Accordion>

<Accordion title="Setup step: APIs could not be enabled" icon="gear">
  The signed-in account lacks the `serviceusage.services.enable` permission on the target project. Either sign in with an account that has `roles/serviceusage.serviceUsageAdmin` on the project, or enable the three APIs manually from the [API Library](https://console.cloud.google.com/apis/library):

- Security Command Center API
- Cloud Resource Manager API
- Service Usage API
  </Accordion>

<Accordion title="No projects listed after OAuth" icon="magnifying-glass">
  OpenComp only lists projects the signed-in account has IAM access to. Sign in with a different
  Google account, or ask an admin to add your account as `roles/viewer` on the relevant projects.
</Accordion>
