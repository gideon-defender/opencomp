## About the AWS integration

OpenComp connects to your AWS account using a **cross-account IAM role** with an **External ID**. No long-lived access keys are created, and all access is scoped to read-only unless you also opt in to auto-remediation with a separate role.

Once connected, OpenComp scans the regions you select and produces findings mapped to common frameworks (SOC 2, ISO 27001, CIS AWS Foundations, PCI DSS, HIPAA).

<Note>
  OpenComp assumes your role from a dedicated AWS principal. You control the trust policy, so you
  can revoke access at any time by deleting the role.
</Note>

## How access works

- **Auth model**: AWS STS `AssumeRole` from a OpenComp–managed principal into a role in your account
- **External ID**: Required in the trust policy so only a specific OpenComp organization can assume the role
- **Permissions**: `SecurityAudit` + `ViewOnlyAccess` managed policies, plus two small inline policies for Cost Explorer reads and SSM document metadata
- **Optional auto-remediation**: Separate per asset-class x region roles (`OpenComp-Remediator-{AssetClass}-{Region}`, e.g. `OpenComp-Remediator-Storage-us-east-1`) can be created to enable auto-fix actions — each role is **only used when you explicitly trigger a fix** for a matching finding. The audit role stays read-only. Connections created earlier may still use the legacy single `OpenComp-Remediator` role as a fallback.

## Prerequisites

Before you begin, make sure you have:

1. An AWS account with permission to create IAM roles
2. Admin access to your OpenComp workspace (OpenComp issues a unique External ID per connection during setup — you never invent one)

## Connect AWS

The OpenComp UI walks you through the full flow and displays the exact CloudShell script to run. The summary below is for reference.

<Steps>
  <Step title="Start the connection in OpenComp">
    Go to **Cloud Tests → AWS → Connect**, pick your AWS environment, and generate the connection. OpenComp issues a unique External ID and displays a CloudShell script pre-filled with it.
  </Step>
  <Step title="Run the script in AWS CloudShell">
    Open [AWS CloudShell](https://console.aws.amazon.com/cloudshell) in the account you want to scan and paste the script. It:

    - Creates an IAM role named `OpenComp-Auditor`
    - Attaches `SecurityAudit` and `ViewOnlyAccess` managed policies
    - Adds small inline policies for `ce:GetCostAndUsage` and `ssm:GetDocument` / `ssm:DescribeDocument` / `ssm:ListDocuments`
    - Sets a trust policy that only allows OpenComp to assume the role when the correct External ID is supplied
    - Prints the new **Role ARN**

  </Step>
  <Step title="Paste the Role ARN and pick regions">
    Copy the Role ARN from the script output and paste it into the OpenComp connection form. Choose the regions you want scanned. The External ID is already on file — paste only the Role ARN.
  </Step>
  <Step title="(Optional) Enable auto-remediation">
    If you want OpenComp to be able to apply fixes, run one CloudShell script per asset-class x region pair shown in the UI (start with the classes and regions you want auto-fix in). Each script creates a separate `OpenComp-Remediator-{AssetClass}-{Region}` role with narrow fix-forward write permissions for that class. Paste each Role ARN into the matching row of the remediation roles table.
  </Step>
  <Step title="Save and run your first scan">
    Click **Save and Connect**. OpenComp validates the role, then queues an initial scan across all selected regions.
  </Step>
</Steps>

The AWS integration evaluates findings across a wide set of AWS services, including:

| Area          | Services                                                                        |
| ------------- | ------------------------------------------------------------------------------- |
| Identity      | IAM, IAM Access Analyzer, Cognito                                               |

- PCI DSS
- HIPAA (where applicable)

## Security model

- **Read-only by default** — the audit role cannot create, modify, or delete resources
- **External ID enforced** — OpenComp refuses to connect unless the External ID in your trust policy matches the server-issued value stored against your connection
- **No static credentials** — OpenComp never stores AWS access keys; short-lived credentials are issued by STS on each scan
- **Revocable at any time** — deleting the IAM role in your account immediately cuts off access

## Troubleshooting

<Accordion title="Access denied during AssumeRole" icon="warning">
  The most common cause is an External ID mismatch. Confirm the value in your role's trust policy
  matches the External ID shown in the connection settings. If they differ, re-run the
  CloudShell script from the settings — the External ID cannot be typed or rotated by hand.
</Accordion>

<Accordion title="Role ARN format error" icon="circle-exclamation">
  OpenComp expects an ARN in the form `arn:aws:iam::ACCOUNT_ID:role/ROLE_NAME`. Make sure you copied
  the role ARN from the CloudShell output, not the account or user ARN.
</Accordion>

<Accordion title="Findings missing for a specific service" icon="magnifying-glass">
  Check that: 1. The role has `SecurityAudit` + `ViewOnlyAccess` attached (the script attaches both)
  2. The region is enabled on your connection 3. The service is turned on in the **Services** tab
  for this connection
</Accordion>

<Accordion title="Auto-remediation isn't available" icon="wrench">
  Auto-remediation requires per-pair `OpenComp-Remediator-{AssetClass}-{Region}` roles (or the legacy `OpenComp-Remediator` role as fallback). Run the CloudShell
  script for the finding's asset class and region, then paste its Role ARN into the matching row of the **remediation roles table** in the connection settings.
</Accordion>
