## About the AWS integration

OpenComp connects to your AWS account using a **cross-account IAM role** with an **External ID**. No long-lived access keys are created, and all access is scoped to read-only unless you also opt in to auto-remediation with a separate role.

Once connected, OpenComp scans the regions you select and produces findings mapped to common frameworks (SOC 2, ISO 27001, CIS AWS Foundations, PCI DSS, HIPAA).

<Note>
  OpenComp assumes your role from a dedicated AWS principal. You control the trust policy, so you
  can revoke access at any time by deleting the role.
</Note>

## How access works

- **Auth model**: AWS STS `AssumeRole` from a OpenComp–managed principal into a role in your account
- **External ID**: Required in the trust policy so only a specific OpenComp organization can assume the role
- **Permissions**: `SecurityAudit` + `ViewOnlyAccess` managed policies, plus two small inline policies for Cost Explorer reads and SSM document metadata
- **Optional auto-remediation**: Separate per asset-class x region roles (`OpenComp-Remediator-{AssetClass}-{Region}`, e.g. `OpenComp-Remediator-Storage-us-east-1`) can be created to enable auto-fix actions — each role is **only used when you explicitly trigger a fix** for a matching finding. The audit role stays read-only.

## Prerequisites

Before you begin, make sure you have:

1. An AWS account with permission to create IAM roles
2. Admin access to your OpenComp workspace (OpenComp issues a unique External ID per connection during setup — you never invent one)

## Connect AWS

The OpenComp UI walks you through the full flow and displays the exact CloudShell script to run. The summary below is for reference.

<Steps>
  <Step title="Start the connection in OpenComp">
    Go to **Cloud Tests → AWS → Connect**, pick your AWS environment, and generate the connection. OpenComp issues a unique External ID and displays a CloudShell script pre-filled with it.
  </Step>
  <Step title="Run the script in AWS CloudShell">
    Open [AWS CloudShell](https://console.aws.amazon.com/cloudshell) in the account you want to scan and paste the script. It:

    - Creates an IAM role named `OpenComp-Auditor`
    - Attaches `SecurityAudit` and `ViewOnlyAccess` managed policies
    - Adds small inline policies for `ce:GetCostAndUsage` and `ssm:GetDocument` / `ssm:DescribeDocument` / `ssm:ListDocuments`
    - Sets a trust policy that only allows OpenComp to assume the role when the correct External ID is supplied
    - Prints the new **Role ARN**

  </Step>
  <Step title="Paste the Role ARN and pick regions">
    Copy the Role ARN from the script output and paste it into the OpenComp connection form. Choose the regions you want scanned. The External ID is already on file — paste only the Role ARN.
  </Step>
  <Step title="(Optional) Enable auto-remediation">
    If you want OpenComp to be able to apply fixes, run one CloudShell script per asset-class x region pair shown in the UI (start with the classes and regions you want auto-fix in). Each script creates a separate `OpenComp-Remediator-{AssetClass}-{Region}` role with narrow fix-forward write permissions for that class. Paste each Role ARN into the matching row of the remediation roles table.
  </Step>
  <Step title="Save and run your first scan">
    Click **Save and Connect**. OpenComp validates the role, then queues an initial scan across all selected regions.
  </Step>
</Steps>

## Migrate from the legacy remediation role

Connections created earlier may use a single `OpenComp-Remediator` role for all auto-fixes. If your connection settings show the legacy-role notice, move to per-pair roles: one `OpenComp-Remediator-{AssetClass}-{Region}` role per asset class and region you want auto-fix in. Each role carries only that pair's fix-forward writes. Fixes use pair roles only — the stored single role is ignored.

<Steps>
  <Step title="Create one role per pair in OpenComp">
    Open the connection settings and find the remediation roles table. Each row names its pair and the exact role to create. Click the terminal button on a row, run that row's script in AWS CloudShell, and paste the printed Role ARN back into the same row. Repeat for every class and region you want auto-fix in — start with `Storage` and `Data`, and add `Security-Global` last (every use of it needs human approval). Click **Save**. The table counts configured pairs (for example, `3/9 configured`).
  </Step>
  <Step title="Confirm the pairs work">
    Every row you need shows **Configured**. Trigger one fix on a matching finding and confirm it runs — or wait for the next scan, since fixes route to pair roles automatically once they exist.
  </Step>
  <Step title="Delete the legacy role in AWS">
    Only delete `OpenComp-Remediator` after the pairs you need show **Configured**. IAM refuses to delete a role that still has policies, so remove its inline policies first (list them to catch leftovers from older script versions), detach anything managed, then delete the role:

    ```bash
    aws iam list-role-policies --role-name OpenComp-Remediator
    aws iam list-attached-role-policies --role-name OpenComp-Remediator
    for p in OpenComp-StorageRemediation OpenComp-ComputeRemediation OpenComp-NetworkRemediation OpenComp-SecurityRemediation OpenComp-MessagingRemediation OpenComp-ExtendedRemediation; do
      aws iam delete-role-policy --role-name OpenComp-Remediator --policy-name "$p" 2>/dev/null || true
    done
    aws iam delete-role --role-name OpenComp-Remediator
    ```

    GovCloud accounts: run this in the GovCloud partition — the role ARN uses `aws-us-gov` throughout.
  </Step>
  <Step title="Confirm in OpenComp">
    Reopen the connection settings. The legacy-role notice is gone and your pair rows still show **Configured**.
  </Step>
</Steps>

<Note>
  Deleting the legacy role before the pairs are ready is safe but degrades auto-fix: findings without a matching pair role fall back to manual guidance until you configure that pair. Nothing breaks and no scan data is lost.
</Note>

## Security model

- **Read-only by default** — the audit role cannot create, modify, or delete resources
- **External ID enforced** — OpenComp refuses to connect unless the External ID in your trust policy matches the server-issued value stored against your connection
- **No static credentials** — OpenComp never stores AWS access keys; short-lived credentials are issued by STS on each scan
- **Revocable at any time** — deleting the IAM role in your account immediately cuts off access

## Monitoring auto-remediation

If you created any `OpenComp-Remediator-*` roles, watch them. OpenComp only assumes a remediation role when you explicitly trigger a fix, so every assume outside a fix you triggered is worth a look. Three signals matter:

| Signal                                           | What it means                                                                                                     | Severity                                    |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| `AssumeRole` on any `OpenComp-Remediator-*` role | A fix ran (or someone probed the trust policy — failed assumes fire too)                                          | Info — reconcile with fixes you triggered   |
| `AccessDenied` from a remediator session         | A fix hit a deny — usually the region guardrail (`DenyOutsideRegion`) or a destructive-action block doing its job | Low — investigate if repeated or unexpected |
| Any use of `OpenComp-Remediator-Security-Global` | The highest-blast-radius role (KMS, CloudTrail, Config, GuardDuty, WAF, Cognito, IAM password policy) was touched | High — every use needs a human review note  |

Subscribe the security on-call email — not an individual inbox. Confirm the SNS subscription email before expecting alerts.

<Steps>
  <Step title="Create the alert topic and subscribe">
    ```bash
    TOPIC_ARN=$(aws sns create-topic --name OpenComp-Remediator-Alerts --query TopicArn --output text)
    aws sns set-topic-attributes --topic-arn "$TOPIC_ARN" --attribute-name Policy --attribute-value '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"events.amazonaws.com"},"Action":"sns:Publish","Resource":"'$TOPIC_ARN'","Condition":{"ArnLike":{"aws:SourceArn":"arn:aws:events:*:*:rule/OpenComp-Remediator*"}}}]}'
    aws sns subscribe --topic-arn "$TOPIC_ARN" --protocol email --notification-endpoint security@example.com
    ```
  </Step>
  <Step title="Create one EventBridge rule per signal">
    All three match `detail-type: AWS API Call via CloudTrail` (management events flow to the default bus automatically — no trail wiring needed):

    - **OpenComp-RemediatorAssume**: `eventSource: sts.amazonaws.com`, `eventName: AssumeRole`, `requestParameters.roleArn` wildcard `arn:aws:iam::*:role/OpenComp-Remediator-*` (plus the bare legacy `OpenComp-Remediator` name)
    - **OpenComp-RemediatorDenied**: `errorCode` in (`AccessDenied`, `AccessDeniedException`), `userIdentity.arn` wildcards `arn:aws:sts::*:assumed-role/OpenComp-Remediator/*` (legacy) and `arn:aws:sts::*:assumed-role/OpenComp-Remediator-*` (per-pair) (no `source` filter — denied calls arrive under the called service's source)
    - **OpenComp-RemediatorSecurityGlobal**: `eventSource: sts.amazonaws.com`, `eventName: AssumeRole`, `requestParameters.roleArn` wildcard `arn:aws:iam::*:role/OpenComp-Remediator-Security-Global`

    ```bash
    aws events put-rule --name OpenComp-RemediatorAssume --event-pattern '{"source":["aws.sts"],"detail-type":["AWS API Call via CloudTrail"],"detail":{"eventSource":["sts.amazonaws.com"],"eventName":["AssumeRole"],"requestParameters":{"roleArn":[{"wildcard":"arn:aws:iam::*:role/OpenComp-Remediator"},{"wildcard":"arn:aws:iam::*:role/OpenComp-Remediator-*"}]}}}'
    aws events put-targets --rule OpenComp-RemediatorAssume --targets 'Id="1",Arn="'"$TOPIC_ARN"'"'
    ```

    Repeat `put-rule` + `put-targets` for the other two rules with their patterns above. Support can provide the exact generated script for all three. GovCloud accounts: ask support for the GovCloud variant — the role ARNs use the `aws-us-gov` partition throughout.

  </Step>
  <Step title="Triage incoming alerts">
    - **Assume alert**: match it to a fix you triggered in OpenComp (finding ID is the STS session name). No match → check for failed assumes (wrong-ExternalId probes) in CloudTrail and rotate nothing yet — probes against a correct trust policy fail closed.
    - **Denied alert**: read `eventName` + `errorCode` in the email body. A `DenyOutsideRegion` hit means a fix tried to act outside its region — expected if you only created roles for some regions. Anything else → open the finding in OpenComp and confirm the action was fix-forward.
    - **Security-Global alert**: confirm a human approved the action, then write the review note. If nobody did, treat it as an incident: the role is human-gated by policy.
  </Step>
</Steps>

<Note>
  For forensics, the same three signals exist as CloudTrail Lake queries (`remediator-assumes-7d`, `remediator-denied-7d`, `security-global-use-30d`) — replace `<EDS_ID>` with your event data store ID. The exact SQL lives with the detector source so the alerts and the queries cannot drift apart.
</Note>

## Troubleshooting

<Accordion title="Access denied during AssumeRole" icon="warning">
  The most common cause is an External ID mismatch. Confirm the value in your role's trust policy
  matches the External ID shown in the connection settings. If they differ, re-run the CloudShell
  script from the settings — the External ID cannot be typed or rotated by hand.
</Accordion>

<Accordion title="Role ARN format error" icon="circle-exclamation">
  OpenComp expects an ARN in the form `arn:aws:iam::ACCOUNT_ID:role/ROLE_NAME`. Make sure you copied
  the role ARN from the CloudShell output, not the account or user ARN.
</Accordion>

<Accordion title="Findings missing for a specific service" icon="magnifying-glass">
  Check that: 1. The role has `SecurityAudit` + `ViewOnlyAccess` attached (the script attaches both)
  2. The region is enabled on your connection 3. The service is turned on in the **Services** tab
  for this connection
</Accordion>

<Accordion title="Auto-remediation isn't available" icon="wrench">
  Auto-remediation requires per-pair `OpenComp-Remediator-{AssetClass}-{Region}` roles. Run the CloudShell script for the finding's asset
  class and region, then paste its Role ARN into the matching row of the **remediation roles table**
  in the connection settings. If the connection previously used the single `OpenComp-Remediator` role, follow [Migrate from the legacy remediation role](#migrate-from-the-legacy-remediation-role) first — that role is no longer read.
</Accordion>
